# MCA Workbook Answers

This document answers the workbook questions using the actual outputs generated by the project in [results/metrics/model_metrics.csv](results/metrics/model_metrics.csv), [results/metrics/project_summary.json](results/metrics/project_summary.json), and the project workflow in [src/train.py](src/train.py).

## 1. AI/ML Business Problem Orientation

### Q1. What is the business problem being solved?
The business problem is to identify customers likely to churn so that retention teams can prioritize intervention and reduce customer loss. This matches the project objective: early churn detection with explainable customer risk assessment.

### Q2. Who are the stakeholders and decision owners?
The primary stakeholders are the retention team, customer success team, and business owner responsible for customer lifetime value. The decision owner is the retention or customer success manager, not an automated system. The model is decision support, not final customer action.

### Q3. What is the prediction timing and unit of analysis?
The model predicts churn at the customer level using one row per customer. The synthetic dataset contains one row for each customer, and the target variable is the churn flag. The prediction is used for customer-level intervention planning.

## 2. Problem Framing and Success Metrics

### Q1. What is the target variable?
The target variable is the churn indicator. In this project, churn is binary: 1 = churned and 0 = not churned.

### Q2. What success metrics were used?
The project used accuracy, precision, recall, F1-score, and ROC-AUC. Confusion matrix analysis was also used. These metrics were computed on the held-out test set.

### Q3. Why were these metrics appropriate?
Churn prediction is usually imbalanced, so it is important to consider both recall and precision. F1-score and ROC-AUC help assess the model’s ability to separate churners from non-churners while keeping the business objective in mind.

## 3. Dataset Understanding and Data Quality

### Q1. What is the source and status of the dataset?
No dataset was provided in the repository at project start. Because the workbook requires a working project and the repository did not contain a real dataset, the project used a synthetic dataset generated in a reproducible way. This is clearly documented as synthetic, not a real-world customer dataset.

### Q2. What data quality checks were performed?
The project checked dataset shape, column names, missing values, duplicate rows, data types, target distribution, and basic descriptive statistics. The data profile was saved to [results/metrics/data_profile.json](results/metrics/data_profile.json).

### Q3. What were the key data quality findings?
The generated dataset contained 1200 rows and 12 columns. The target distribution was imbalanced in the synthetic data, with churn value 1 occurring at 0.8067 and churn value 0 at 0.1933. This shows class imbalance and supports the use of stratified splitting and balanced-class models.

## 4. Data Preparation and Exploratory Analysis

### Q1. What cleaning steps were applied?
The project cleaned missing values, converted invalid values to a consistent format, coerced data types when appropriate, removed duplicate rows, and standardized the target field. These steps are implemented in [src/preprocessing.py](src/preprocessing.py).

### Q2. What exploratory analysis was performed?
The project generated a data profile and produced churn-related exploratory summaries. This included dataset structure, churn distribution, and relationships between customer behaviour variables and churn. The project also created model comparison and confusion matrix outputs.

### Q3. What did the EDA reveal?
The exploratory process confirmed that the generated churn dataset has a clear target signal and that churn risk is associated with contract type, support contact frequency, usage patterns, satisfaction, and recency of login. These findings are consistent with the synthetic data generation logic and were used to build relevant features.

## 5. Feature Engineering and Model Design

### Q1. What features were used?
The project used the available customer attributes such as age, tenure, monthly charges, contract type, payment method, support contacts, average usage hours, satisfaction score, and days since last login. The project also created engineered features such as ratios and behavioural indicators where useful.

### Q2. What engineering was done?
The feature engineering layer created a small set of meaningful features, such as customer value and support contact rate, while keeping the design simple and academically explainable.

### Q3. Why was the model design simple?
The project follows the academic requirement for a clear ML workflow: simple preprocessing, two core models, and interpretable comparison. This avoids unnecessary complexity and keeps the approach easy to explain in a viva.

## 6. Model Training and Comparison

### Q1. Which models were trained?
The project trained a logistic regression model and a random forest model. A tuned random forest was also trained using a small grid search. The models are defined in [src/train.py](src/train.py).

### Q2. How was the data split?
The dataset was split using an 80:20 train-test division with stratification on the target variable. This preserves the churn distribution in both sets and reduces sampling bias.

### Q3. What was the model comparison result?
The actual test-set results are:

- Logistic Regression: Accuracy 0.5792, Precision 0.8394, Recall 0.5928, F1 0.6949, ROC-AUC 0.5723
- Random Forest: Accuracy 0.7167, Precision 0.8182, Recall 0.8351, F1 0.8265, ROC-AUC 0.5942
- Random Forest Tuned: Accuracy 0.7125, Precision 0.8079, Recall 0.8454, F1 0.8262, ROC-AUC 0.5756

The best F1-score was achieved by the random forest model, followed closely by the tuned random forest.

## 7. Model Evaluation and Validation

### Q1. Which evaluation metrics were used?
The project used accuracy, precision, recall, F1-score, ROC-AUC, and confusion matrix output.

### Q2. What was the model performance on the test set?
The random forest model had the strongest F1-score and recall among the evaluated models, making it the most suitable for identifying churners in the synthetic test set.

### Q3. Did the project check overfitting?
Yes. The project compared training and test performance qualitatively through the model comparison and used a validation-based tuning workflow. The random forest tuning did not produce a substantial improvement over the untuned version, so the simpler model remained a valid choice for the final academic implementation.

## 8. Explainable and Responsible AI

### Q1. How was explainability handled?
The project provides a simple decision-support explanation using feature importance and customer-level risk output. The synthetic project also exposes the churn probability and risk band, which are more interpretable than black-box only outputs.

### Q2. What responsible AI considerations were included?
The project addresses privacy, bias awareness, human oversight, and the limitation that automated decisions should not replace human review. It also avoids making final decisions without human judgment.

### Q3. What are the main limitations?
The dataset is synthetic. Business results cannot be generalized to a real customer base without validation on a real churn dataset. The project is therefore an academically appropriate prototype and not a production deployment.

## 9. Prediction and Decision Support Design

### Q1. How do customers get risk scores?
The project generates churn probability for each customer and converts it into a risk band: LOW, MEDIUM, or HIGH.

### Q2. What is the decision-support output?
The output includes customer ID, churn probability, risk band, and the main factors contributing to risk. This supports the retention team in prioritizing actions.

### Q3. Why is this decision support and not automated decision-making?
The project is designed to assist human decision-makers. It does not automatically remove or alter customer accounts, and it is explicitly kept as a business-support tool rather than a final customer decision system.

## 10. Model Robustness and Optimization

### Q1. What threshold analysis was performed?
The project evaluated probabilities using thresholds of 0.30, 0.40, 0.50, 0.60, and 0.70. This helps understand trade-offs between precision and recall at different decision points.

### Q2. What was the threshold result?
The threshold analysis shows the expected pattern: lower thresholds increase recall and flagged customer count, while higher thresholds improve precision but reduce recall. The project used a simple threshold-based risk approach aligned with business needs.

### Q3. What optimization was performed?
The project used a small grid search for the random forest model to tune the main parameters and compare the tuned model against the baseline model. The tuned version was not meaningfully better than the untuned forest on the test set, so the simpler model remained a reasonable choice for academic clarity.

## 11. ML Deployment and Monitoring Readiness

### Q1. What is the deployment design?
The project follows a simple deployment concept: customer data -> preprocessing -> trained model -> churn probability -> risk classification -> decision support. This is documented as a lightweight academic deployment design.

### Q2. What monitoring is recommended?
The project recommends monitoring data drift, prediction drift, and model performance when actual churn labels become available. Monitoring should include precision, recall, F1-score, and ROC-AUC over time.

### Q3. What is the rollback concept?
The project stores model artifacts and keeps the trained model versioned. If the model degrades or a new model version is required, the project can revert to the prior artifact and retrain based on updated data.

## 12. Final AI/ML Recommendation and Roadmap

### Q1. Which model is recommended?
The random forest model is recommended as the final model for the synthetic project because it had the strongest F1-score and higher recall on the test set, which makes it more useful for identifying churners in a support workflow.

### Q2. What is the project roadmap?
The next steps are to replace the synthetic dataset with a real customer churn dataset, validate the model on live business data, tune thresholds based on business priority, and expand monitoring and governance.

### Q3. What is the final recommendation?
The current implementation is a successful academic churn prediction prototype. It is suitable for demonstration, documentation, and viva discussion, but it should not be treated as a production-grade customer decision system without real-world validation.
